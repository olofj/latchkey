## 1. Why

F19-options §1 has the evidence: build 0.1 was rejected for beta review on
2026-09-25, and structurally a reviewer can reach nothing past the gate — no
tailnet identity, no gateway, no token. It costs the routes and stops. This
spec picks, and it picks from what the code allows rather than from the
brief. Four facts, each checked on 2026-09-25 at `b829b5d98`:

1. **The node already takes an auth key; a running node takes one too.** At
   creation, `TailscaleNode.swift:71-72` passes `config.authKey` to
   `tailscale_set_authkey`, which is `tailscale.go:665-670` setting
   `Server.AuthKey`. That is the test hook's path
   (`TSNetManager.launchAuthKey`, `TSNetManager.swift:273-275`). There is a
   second path for a node that is *already up* at `NeedsLogin`, which is the
   gate's situation: LocalAPI `POST /start` with `Ipn.Options.AuthKey`
   (`LocalAPIClient.swift:121-129`, `Types.swift:230-233`), which
   `LocalBackend.Start` hands to a fresh control client
   (`ipn/ipnlocal/local.go:3211`). No node restart, no change to
   `Configuration`, and the key never enters the workspace.
2. **A refused key is silent today.** Control answers a bad key with a
   `RegisterResponse.Error` (the harness's `testcontrol.go:982-986`,
   `"invalid authkey"`); the backend forwards it as `Notify.ErrMessage`
   (`Types.swift:44`). Nothing in `app/` or `TSNet/` reads `ErrMessage`
   (grep, 2026-09-25). The node would sit at `NeedsLogin` and the gate would
   say "Login Required" as if nothing had been tried.
3. **A real gateway cannot be the demo.** A sign-in link is redeemable for
   `min(300 s, ttl)` from minting (`fake_gateway.py:26-27, 198`, read from
   `token_auth.py:870, 3005`), so no token can be written into review notes
   days ahead. `fake_gateway.py` serves the real 0.7.1 frontend byte for byte
   and emulates the server (`fake_gateway.py:1-12`); its credentials are its
   own invention (D10), so a standing demo token is its rule to make.
4. **Nothing records video, and the Swift redactor does not know auth
   keys.** `look.sh:44` and the suite scripts take stills with
   `simctl io … screenshot`; no `recordVideo` anywhere. The Go-side log
   filter redacts `tskey-…` (`latchkey_locallog.go:186, 200`); the app's
   `LogRedaction.swift` has no such rule, so a key interpolated into an app
   log line would be kept.

**Where the brief was wrong**, so nobody builds from it:

- "`-AuthKey`/`APERTURE_AUTHKEY` is a Debug-gated test hook (DECISIONS.md:674)."
  It is gated by `LATCHKEY_TEST_HOOKS`, compiled only into the **Testing**

- "Key stored in Keychain." No Keychain item exists in the app, TailscaleKit

  phone is a liability with no flow behind it. §5 does not persist it; §8 Q3

- "F19" was free when the brief was written and taken by the time this was

- "The real 0.7.1 dashboard fronting either `fake_gateway.py` or a real

## 2. What the owner sees

### 2.1 The reviewer, on a fresh install

1. The gate: F11's introduction, **Sign in to Tailscale**, and under it a
   plain second button, **Sign in with an auth key**. Both visible to every
   user on every build; nothing hidden (2.3.1).
2. The auth-key sheet. Three sentences: an auth key joins this phone to a
   tailnet without a browser sign-in; tailnet admins make them in the admin
   console; use one only from a tailnet you mean to join, because Latchkey
   will open a dashboard on it. A field, **Join**, and Cancel.
3. Paste, Join. The sheet says "Joining…"; the gate reports Running; the
   sheet closes.
4. The picker shows **Joined `&lt;tailnet name&gt;`** and the one gateway it found,
   and waits for a tap (§4.2: no auto-select after an auth-key join).
5. The token sheet names the gateway (R23); the reviewer pastes the demo
   token from the notes. The real 0.7.1 dashboard loads with the seeded
   sessions.
6. Share: the reviewer shares a link from Safari (the Latchkey icon, F3
   stage 2), opens Latchkey, picks a session, Send; the message appears in
   that session. Settings: gateway switcher, Diagnostics, Reset.

### 2.2 Failing

- **Control refuses the key** (wrong, expired, revoked): within a second the
  sheet shows *The tailnet refused this key: `&lt;control's message&gt;`. Ask for
  a new one.* The Join button returns. The node stays at `NeedsLogin`; the
  gate is unchanged behind the sheet.
- **No answer in 20 s** (no network, control unreachable): *The tailnet did
  not answer.* Try again, and the gate's existing states (F4 G2/G6, F8 G7)
  carry on saying what the node is doing.
- **The node is not at `NeedsLogin` yet** (still starting): Join is disabled
  with *Waiting for the node…* until it is.
- **Joined, nothing found** (a policy mistake on the review tailnet): the
  picker's existing empty state (F4 P-states) plus the tailnet name it
  joined, so the owner's first question — *which* tailnet? — is answered on
  screen.
- **Malformed input** (no `tskey-` prefix, whitespace inside, under 20
  characters): the sheet says what an auth key looks like and does not call
  the node.

### 2.3 The owner, before a submission

`scripts/review-tailnet.sh rotate` prints a fresh reviewer key and demo token
once, to the terminal. `make review-media` regenerates the walkthrough video
and the screenshots. `scripts/review-tailnet.sh check` proves the demo node
is up with a trusted certificate and the token redeems. The notes in §4.7 get
the two secrets pasted in. Every one of these fails loudly rather than
producing something half-true.

## 3. Non-goals

- **Not F19-options' C** (a demo inside the app) and **not B1** (an SSO
  identity handed to Apple). B2 is the only route where the reviewer runs the
  real app against a real tailnet with no credential that opens an IdP.
- **Not persisting the auth key**, in Keychain or anywhere (§1, §5).
- **No change to the split tunnel, the manual-entry gate or the single
  destination.** The reviewer's gateway is a tailnet host found by the
  ordinary sweep.
- **No Funnel, no public host.** The demo node is reachable only from the
  review tailnet.
- **Not the reply to Apple**, and not App Store metadata beyond the notes
  (privacy policy URL, nutrition labels: §8).
- **Not device automation.** What only a phone can capture is listed in
  §4.8 and recorded by hand.

## 4. Design

### 4.1 The sheet: `App/Tailnet Status/AuthKeySheet.swift` (new)

Modelled on `TokenEntrySheet`. `AuthKeyInput.parse(_:) -&gt; Result&lt;String,
Refusal&gt;` is pure (Foundation only, host-tested like `TokenInput`): trims,
strips the wrapping punctuation `TokenInput` strips, requires the `tskey-`
prefix, no interior whitespace, at least 20 characters. It does not
distinguish `tskey-auth-` from `tskey-client-`; control does.

Identifiers, the contract with §6: `gate-authkey-button` (the gate),
`authkey-sheet`, `authkey-field` (a `SecureField`; the key is a secret and
the video must not show it), `authkey-join`, `authkey-cancel`,
`authkey-error` (the refusal text), `authkey-joining` (the progress row).

The button lives in `ConnectionGateView` under `GateLoginButton`
(`ConnectionGateView.swift:72`), shown on the same condition as the primary
button. Not on `LoginBanner` (mid-session `NeedsLogin`,
`DashboardRootView.swift:581-627`): that state is a re-login after expiry,
outside a review window.

### 4.2 Applying it: `TSNetManager.join(authKey:)` and `TSNetModel.controlError`

- `TSNetManager.join(authKey: String) async throws` calls
  `localAPIClient.start(options: Ipn.Options(UpdatePrefs: nil, AuthKey:
  key))`. Precondition: `model.state == .NeedsLogin` and a LocalAPI client
  (`localAPIClient`, set in `startTailscale`, `TSNetManager.swift:288-292`);
  otherwise it throws `notReady`, which the sheet shows as *Waiting for the
  node…*. The key is a parameter and a local; it is not stored on the
  manager, the model, the workspace or the definition.
- `TSNetModel` gains `@Published var controlError: String?`, set from
  `notify.ErrMessage` where `TSNetModel.swift:93-128` reads the other
  `Notify` fields, cleared on any state change to `Running`. The sheet shows
  it as the refusal. **To measure first** (§9 will record it): that
  `LocalBackend.Start` with a bad key produces an `ErrMessage` on the bus
  and leaves the state at `NeedsLogin`, on the L2 harness. If it does not, the
  fallback is `TailnetLogout`'s shape — read the failure from the node's
  `/status` after a bounded wait — and the spec is amended.
- `StatusViewModel` gets `joinWithAuthKey(_:)`: parse, call `join`, and race
  the model's next `Running` / `controlError` against the 20 s timeout.
  `authSessionEndedGeneration` is not reused; the sheet has its own state.
- After a successful join, `Workspace.joinedByAuthKey = true` (in memory
  only). `DashboardRootView` passes `autoSelectSingle: !joinedByAuthKey` to
  the picker (`GatewayPickerView.swift:26-27`), and the picker's header
  shows *Joined `&lt;model.tailnetName&gt;`*. This is the mitigation for the risk
  F19-options §4.2 states: a user talked into pasting a stranger's key is not
  carried straight to the stranger's token sheet; the tailnet's name and a
  tap stand between. The token sheet's R23 naming stays.

### 4.3 Logging and redaction

- The sheet and the manager log *that* a join was requested and its outcome,
  never the key or its prefix. (`TimingHarness.swift:202, 432` log a
  14-character prefix; that file is `#if LATCHKEY_TEST_HOOKS` and stays.)
- `LogRedaction.scrub` gains the Go filter's rule: `(?i)\btskey-[^\s"'&lt;&gt;\\`]*`
  → `tskey-…`, so a key that reaches `Logger.log` by any path (an
  interpolated error, a URL, a future line) is cut. One case in
  `scripts/test-log-redaction.swift`.
- `LogRedaction` already keeps control's login links out of the app log
  (`LogRedaction.swift:45-52`); an auth-key join never receives one.

### 4.4 R44, and what stays Testing-only

R15's reason was a paired Mac joining the app to a foreign tailnet through a
launch argument with no user present (`TestHooks.swift:11-14`). The UI path
needs a tap and a paste. So:

- `TSNetManager.launchAuthKey()` / `launchEphemeral()` and every reader of
  `TestHooks` are unchanged and remain Testing-only. R15's binary check
  (DECISIONS 2026-09-20: `APERTURE_AUTHKEY` absent from the non-Testing
  binaries) becomes acceptance criterion §7.3 and is extended: the Release
  binary must *contain* the sheet's strings (the path is not hidden) and
  must *not* contain `APERTURE_AUTHKEY` (the hook is not promoted).
- R6 (a real install is never ephemeral) holds: the UI path sets no
  ephemeral flag; the key's own attributes decide at control, and the
  reviewer key is not ephemeral (§4.6).
- `../PLAN-REVISIONS.md` gets **R44**: "An auth key can be pasted at the gate
  in every build; the launch-argument key stays Testing-only."

### 4.5 The demo server: `fake_gateway.py` in demo mode

The choice the brief asked for, with the trade-off:

| | The fake, in demo mode | A real KiroCrew with a cheap model and a spend cap |
|---|---|---|
| What the reviewer sees | the real 0.7.1 frontend over seeded, unchanging sessions; a sent message appears in the session (the fake journals posts and answers as the server would) but nothing replies | the same frontend, and an agent that answers |
| The token | a standing demo token the fake accepts for as long as it runs — its own rule, since its credentials are its own (D10) | a link dies 300 s after minting (§1.3); the reviewer would need one minted on demand, which needs the owner on hand |
| Risk | none: no tools, no model, no data | tool execution and spend by a stranger; the cap bounds cost, not what the tools do |
| Upkeep | the pin ages (0.7.1); fine for showing | KiroCrew upgrades under it; the token problem never goes away |

**Recommendation: the fake.** A reviewer is checking that the app does what
the notes say, not that an agent is clever; the notes say plainly that the
demo dashboard does not run an agent. The real-agent option is closed by the
300 s link window alone.

Two flags, both refused by the suites (`test-session.sh` never passes them,
and `gateway_check.py` fails if `/__state` reports `demo: true` without
`--demo`):

- `--plain`: listen on plain HTTP for `tailscale serve` to front. Everything
  else stays as behind serve: cookies named for the emulated 5476 listen port
  (`fake_gateway.py:31-34`), `Secure` set (the phone sees HTTPS), the Host
  allowlist on `--host`.
- `--demo &lt;seed.json&gt;`: a fixed token (≥ 16 characters of `TokenInput`'s
  charset, `TokenInput.swift:41-48`) that redeems any number of times and
  survives `/__restart`; seeded slots and messages with fixed timestamps so
  two captures are byte-alike; `/__state` reports `demo: true`; the control
  port binds loopback only. The seed is `testing/harness/demo-seed.json`,
  three sessions ("notes", "research", "inbox") with a handful of messages
  each and no name, host or text of the owner's.

The fake already answers discovery's recognition pair (M5 uses it as the
`gw` peer), so the sweep finds it unchanged.

### 4.6 The review tailnet: runbook and `scripts/review-tailnet.sh`

A separate tailnet under a dedicated identity that owns nothing else.
Settings once, in the admin console: MagicDNS on, HTTPS certificates on
(for `tailscale serve`), device approval off, tailnet lock off. Policy:

```json
{
  "tagOwners": { "tag:demo": ["autogroup:admin"], "tag:reviewer": ["autogroup:admin"] },
  "grants": [
    { "src": ["tag:reviewer"],    "dst": ["tag:demo"], "ip": ["tcp:443"] },
    { "src": ["autogroup:admin"], "dst": ["tag:demo"], "ip": ["*"] }
  ]
}
```

Nothing else is granted: reviewer nodes reach the demo node on 443 and
nothing more, not each other, not the admin's devices. Discovery accepts a
tagged gateway regardless of owner (`GatewayCandidates.swift:64-70`), and a
tagged node's key does not expire by default, which is F19-options §4.2's
"expiry disabled" for free (verify in the console when the node first
appears).

**The node.** One small always-on Linux host that is *not* on the owner's
tailnet — a container or VM, or a second `tailscaled` in userspace mode on
an owner machine with its own state and socket. `scripts/review-node.sh`,
run on it: install tailscale, `tailscale up --auth-key &lt;tag:demo key&gt;
--hostname demo`, copy `testing/harness/` only, `make bundle`, a systemd
unit for `fake_gateway.py --plain --port 8444 --host demo.&lt;tailnet&gt;.ts.net
--demo demo-seed.json` with the token in an env file (mode 600), and
`tailscale serve --bg --https=443 http://127.0.0.1:8444`. The host holds the
repo's harness directory, the pinned wheel and the token; no key of the
owner's, no log of his, no session.

**Keys.** A reusable, pre-authorized, **non-ephemeral** `tag:reviewer` auth
key, 90 days (the maximum). Non-ephemeral so a reviewer's node survives a
relaunch without the key (§5); the cost is stale reviewer nodes, which
rotation removes. `scripts/review-tailnet.sh`, on the Mac, with an OAuth
client for the review tailnet (`auth_keys` and `devices` scopes) in
`~/.latchkey-review/oauth` (600), the way `app/.asc-key` holds the ASC key:

- `rotate`: revoke every earlier `tag:reviewer` key, delete `tag:reviewer`
  devices not seen for 7 days, mint a new key (`POST
  /api/v2/tailnet/-/keys`, reusable, preauthorized, `tag:reviewer`,
  `expirySeconds` 7776000, description dated), generate a new demo token,
  and print both **once** to the terminal. With `REVIEW_NODE_SSH` set it
  updates the node's env file and restarts the unit; otherwise it prints the
  two commands to run there. Nothing is written to disk on the Mac.
- `check`: over SSH to the node (or locally if run there):
  `https://demo.&lt;tailnet&gt;.ts.net/manifest.json` names "Kiro Crew",
  `/api/auth/me` answers 403 with `X-Auth-Required`, the certificate chain
  validates against the system store, and `/?token=&lt;demo&gt;` redeems twice.
  This is F19-options §6's "review gateway check", with `gateway_check.py`'s
  client.
- `status`: the tailnet's devices, keys and their expiries, so the owner can
  see a key about to lapse mid-review.

**Between submissions:** `rotate`, then `check`, then paste into the notes.
The old key is dead the moment the new one exists, so a leaked notes field
from a previous review opens nothing.

### 4.7 The review notes

For App Review Information → Notes, with the two secrets pasted in. Under
4000 characters; native value first, for 4.2:

&gt; **What Latchkey is.** A single-purpose client for a KiroCrew dashboard the user runs on their own computer. The computer is not on the public internet; Latchkey reaches it over the user's private Tailscale network. The native parts are the point: the app embeds its own userspace Tailscale node (no VPN profile, no effect on the rest of the phone's traffic), routes only that network's hosts through it, discovers the dashboard by probing the network's peers, switches between gateways, keeps the dashboard's session native (sign-in sheet, QR scan, sign-out, reset), and adds a share-sheet extension and a Shortcuts action that send links and files from other apps into a session. The web view shows one origin and nothing else; every other link opens in the user's browser after a tap.
&gt;
&gt; **Why a demo network is needed.** A user's dashboard is private to their network, so we run a review network with one demo dashboard on it. It serves the dashboard's real frontend over scripted sessions; it does not run an AI agent, so nothing replies to messages. Nothing on it belongs to a real person.
&gt;
&gt; **How to test.** 1. On the first screen tap *Sign in with an auth key* and paste: `&lt;AUTH KEY&gt;`. Tap Join; the app joins the review network. 2. It finds the demo dashboard; tap it. 3. ### 4.9 The L2 harness: `/reset?authkey=&lt;key&gt;`

`testing/tsnet-harness/main.go:946-947` parses `auth` and `machine`; it gains
`authkey`, which sets `testcontrol.Server.RequireAuthKey`
(`testcontrol.go:57`) *and* `AuthKey` on each harness peer's tsnet server
(`node.go`), because testcontrol requires the key of every node
(`testcontrol.go:982`, "for all nodes"). `GET /state` reports
`requireAuthKey: true` and never the key. **Caveat, read from
`testcontrol.go:1116-1123`:** `RequireAuth` consults only `nodeKeyAuthed`, so
with `auth=1` a node presenting the right key is still sent to the login
page, unlike real control. The tests use `authkey=` without `auth=1`; a
faithful model would be a vendored change (its own commit, R16) and is not
needed here.

**Invariants this must not break** (see `../../app/AGENTS.md`):
- the split tunnel decides what goes through the proxy; only tailnet hosts do
  — the demo gateway is a tailnet host found by the ordinary sweep;
- `allowFailover` stays false;
- ATS stays on with no exceptions; HTTPS only — `tailscale serve`'s
  publicly trusted certificate, no test CA on a reviewer's phone;
- D1: no app or node logs leave the device — the reviewer's included;
- a vendored-tree change is its own commit (R16) — none is planned; §4.9
  says where one would be.

## 5. State and migration

- **The auth key is not persisted**, anywhere: not in `WorkspaceDefinition`
  (`Workspace.swift:84-86` already says "NOT stored in the definition"), not
  in the Keychain, not in `UserDefaults`, not in a log. It is a parameter of
  one LocalAPI call. Consequence: a reviewer node that is logged out (R32
  Reset, or a key revoked at control) needs the key pasted again. That is
  the design, and it is why the reviewer key is non-ephemeral (§4.6).
- `hasEverConnected` is set on `Running` as today (`Workspace.swift:155-156`),
  so F11's introduction leaves after an auth-key join too. `joinedByAuthKey`
  is in memory only and false on every launch.
- R32 is unchanged and exercised: a reviewer's Reset expires their node's
  key at control, so a tidy reviewer leaves nothing; an untidy one leaves a
  node that `rotate` removes.
- The demo node's state is the runbook's (§4.6), and `docs/TESTFLIGHT.md`
  gets a "Before a review" section pointing here.
- Nothing written by a previous version changes meaning.

## 7. Acceptance criteria

1. On the L2 harness with `authkey=` set, the app joins from the gate with
   the key typed into the sheet and the dashboard loads over the tailnet.
   Instrument: the dash peer's journal entry from the app node.
2. A refused key is on screen within 20 s with control's reason, and never
   silent. Instrument: `authkey-error` in the accessibility tree; the app
   log's join-outcome line.
3. The Release binary contains the sheet's strings ("Sign in with an auth
   key", "The tailnet refused this key") and does not contain
   `APERTURE_AUTHKEY` or `-AuthKey`. Instrument: `strings` on
   `Latchkey.app/Latchkey` from `make tf UPLOAD=0`, in `testflight.sh`'s
   preflight, failing the export otherwise.
4. The literal key is in no file of the app container and in no log after a
   join. Instrument: `test-tailnet.sh`'s scan, which must also find the
   redacted marker.
5. `make review-media` produces, from a clean checkout with the harnesses
   only, one video of 50–80 s and seven stills per device class at sizes in
   App Store Connect's lists, and exits non-zero otherwise. Instrument: the
   script's own `sips` and duration checks, and its exit code.
6. `review-tailnet.sh check` passes within an hour before each submission
   (F19-options §7.3), and `rotate` has run since the previous one.
   Instrument: the script's output and the key's description date in
   `status`.
7. Apple's verdict: the build's review status. Instrument: App Store
   Connect.

## 8. Open questions and owner actions

1. **F19-options Q1–Q3 still stand.** This spec assumes the answer to
   "external testers or the App Store?" is yes; if internal testing is
   enough, F19-options §4.0 is the whole fix and nothing here is built.
2. **Where does the demo node live?** A small VPS or container, or a second
   userspace `tailscaled` on chonk with its own state directory. Either
   works with `review-node.sh`; the second keeps no new machine but puts a
   review-tailnet process on an owner machine.
3. **Store the key after all?** §1 and §5 say no. If a reviewer's node being
   logged out mid-review (a Reset they tried) is worth avoiding a second
   paste, the alternative is a Keychain item with
   `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`
   (`BackupExclusion.swift:27-29`), wiped by Reset, and a re-join on
   `NeedsLogin`. It adds a secret to protect and a path to test.
4. **KiroCrew's frontend, served to Apple** — F19-options §8 Q6. The demo
   node serves the pinned wheel's bundle to a third party. Check the licence,
   or ask.
5. **iPad: keep the claim?** The media target produces the 13" set and runs
   the walkthrough on an iPad simulator, which is the first time anything
   here runs on one (F19-options §2.2). If it shows layout faults, they are
   their own spec; dropping to iPhone-only (`TARGETED_DEVICE_FAMILY = 1`)
   removes both the set and the risk.
6. **App Store metadata this does not cover:** a privacy policy URL (required
   for App Store review, not for TestFlight), the privacy nutrition labels
   (D1 makes them short), a support URL. Owner actions in App Store Connect.
7. **The share extension's privacy manifest** (F19-options §2.2), before the
   next upload; its own commit.
8. **Unverified while writing:** whether App Review Information accepts a
   video attachment in the beta-review flow as it does for App Store review;
   whether `LocalBackend.Start` with a bad key yields an `ErrMessage` rather
   than only a log line (the first thing to measure, §4.2); which 6.9" and
   13" simulators this Mac has installed (the script names what is missing);
